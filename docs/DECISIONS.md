# Decisions

Choices made while building Tailor, with the reason for each.

## Project setup

- **uv and Python 3.12.** `.python-version` pins 3.12, the oldest version the app supports, so the tests run on the oldest version a user might have. `pyproject.toml` sets `package = false` because Tailor is an app, and nothing installs it as a library.
- **Dependencies so far.** `pydantic` describes edits and slots, which cross to the interface as JSON and need checking when they come back. `pypdf` counts the pages in a compiled PDF. `pytest` is a dev dependency.
- **Private data stays out of git.** `data/private/` is ignored. It holds the real resume, pasted postings, tailored outputs, the facts bank and the database. Tests use only the fake resume and posting in `tests/fixtures/`.

## Template engine

- **Slot positions are character indexes** into the source string, because that is how Python slices strings. A test reads the sample as bytes, applies no edits and compares the bytes, so the round trip is exact at the byte level too.
- **A slot kind is a name plus an argument number**, such as `kind="subheading"` and `arg=2`. Both are plain values, so a slot turns into JSON for the interface without a custom encoder.
- **Plain text in, escaped LaTeX out.** Models and the interface see slot text as plain text. `plain_to_tex` escapes every special character, so model output can't add commands. Text that didn't change keeps its original bytes, so accepting nothing reproduces the input file exactly.
- **A small markup mapping.** `\textbf{x}` shows as `**x**`, `\emph{x}` and `\textit{x}` as `*x*`, `$\sim$` as `~`, `$|$` as `|`, ``` ``x'' ``` as curly quotes and `--` as an en dash. A slot that uses any other command is shown as raw LaTeX, and only the user can edit it.
- **Hand-typed LaTeX is allowlisted.** A hand edit may only use `\textbf \emph \textit \underline \href \sim \textbackslash \textless \textgreater`. Checking brace balance and the skeleton isn't enough on its own, because `\section{...}` inside a bullet's braces keeps both intact. The allowlist also blocks font-size and spacing commands, so an edit can't shrink the page to fit.
- **Removing a bullet is the one structural edit**, because trimming to one page needs it. It removes the whole `\resumeItem{...}` line, and the skeleton check expects that line to be gone.
- **Section order is locked**, so no edit can add a Summary or Objective section.

## Truth checks

- **Grounding sources.** A rewrite is checked against the bullets and facts it cites, plus its own original bullet and the heading of the role or project it sits under (company, title, project name and stack). The heading is there so a bullet can name its own employer or stack. Anything else has to be cited.
- **What counts as a claim.** Numbers, including spelled-out ones, `k` and `M`, percentages and ratios like `2x` or `twice`. Capitalized words that aren't ordinary sentence starts. Mixed-case words like `iPhone` or `DynamoDB`. Any skill in the lexicon. Lowercase tool names that aren't in the lexicon slip through; adding them to `skills.txt` closes the gap one name at a time.
- **No derived numbers.** A percentage needs a percentage in the source, and a ratio needs a ratio. "75% fewer calls" from "12,000 to 3,000" is correct math, but a hiring manager can't check a number the resume never stated, and a model that does arithmetic can also do it wrong.
- **Style rules only blame what the rewrite added.** Lists of three, contrasts and AI mentions are compared with the source bullets, and a pattern that was already there isn't flagged. Em dashes, stock words, self-comparisons and numbers with no unit are flagged wherever they appear.
- **The lexicon lives in a text file** (`app/core/skills.txt`) so adding a skill or alias needs no code change. A leading `=` makes a name case-sensitive, which keeps "go fast" from counting as Go. One-letter names like C and R also need list context, so "Series C startup" doesn't count as knowing C.
- **Coverage only counts real skills.** A skill counts as covered only when the scored resume shows it and the base resume or facts bank backs it up. Required coverage is covered divided by the required skills you have. Required skills you don't have aren't in the denominator, because no honest rewrite can add them.
- **Posting tiers.** Skills under a requirements heading are required, under a preferred or nice-to-have heading preferred, and a line saying "a plus" or "preferred" is preferred wherever it sits. If the posting has no requirements heading, every skill found is required. A skill keeps its strongest tier.
- **The facts bank is a JSON file** in the private data folder. It's small, the user may want to read or back it up by hand, and it's written to a temporary file and then swapped in, so a crash can't leave half a file. Fact ids are never reused after a delete, so a run that cited `f3` still points at the same fact.

## Model providers

- **One interface, checked output.** Each provider only sends a request and streams back text. The shared `Provider.complete` parses that text against the step's Pydantic schema and raises `BadOutput` if it doesn't fit, so the pipeline never handles an unchecked reply, whichever provider produced it.
- **Strict schemas, written out in full.** Step replies forbid unknown fields and make every field required (a field that may be empty is `str | None` with no default), which is what the providers' structured-output modes expect. Pydantic puts nested models under `$defs`; `json_schema` inlines them because not every provider follows `$ref`.
- **Plain synchronous calls.** The interface calls Python through pywebview, which runs each call on its own thread, so a provider can block while it streams without freezing the window. That keeps each provider readable from top to bottom, with no event loop.
- **Retries.** Rate limits and server errors are retried up to three tries in all, waiting for the provider's Retry-After when given (capped at 30 seconds) and otherwise 2, then 4 seconds. A rejected key or a malformed reply isn't retried, because trying again gives the same answer.
- **Claude API through the official SDK.** `anthropic` handles the request format, streaming events and error types, so the provider is mostly a mapping from SDK results to the app's own errors. The SDK's built-in retries are off (`max_retries=0`) so every provider retries the same way, in `Provider.complete`.
- **Claude API defaults.** The default model is `claude-sonnet-5-5`, which gives strong rewrites at a lower price per run than Opus. The instructions and the base resume are two system blocks with a cache breakpoint on the resume, so the Score, Rewrite and Done steps after the first read that shared prefix from the cache. Effort is left at the model's default unless set in Settings.
- **Refusal fallback.** Requests send `fallbacks: "default"` with its beta header, so a request the model's safety checks decline is rerun on a fallback model in the same call instead of failing the step. If an account rejects the option, the provider drops it and sends the request again.
- **Gemini through the `google-genai` SDK**, with `response_json_schema` for structured output. The default model is `gemini-flash-latest`, an alias that follows Google's current Flash model and is covered by the free tier. The instructions and resume go first, in the system instruction, so Gemini's automatic caching can reuse them across steps. Thinking parts are skipped, so only the answer streams to the interface, but thinking tokens still count toward the cost. `max_output_tokens` is doubled for the same reason: thinking uses up the same limit.
- **`httpx2` for plain HTTP.** Both AI SDKs already depend on `httpx2`, a drop-in fork of `httpx` with the same API, so Ollama and the web import use it too instead of adding a second HTTP library.
- **Ollama over its local HTTP API.** It has no official Python SDK in the stack, and the `/api/chat` call is one POST that streams a JSON object per line, so plain `httpx2` keeps it short. The context window is raised to 16,384 tokens because Ollama's default is too small for the instructions, the resume and a posting together. A missing model gets a message with the `ollama pull` command, and a refused connection says that Ollama isn't running.
- **Claude Code provider ("Claude Code (Pro plan)").** It runs each step through the `claude` command in print mode, so the work is billed to a Claude subscription instead of API credits. It's for personal use: it drives the user's own signed-in copy of Claude Code on their own computer, and it isn't a way to serve other people from one subscription.
- **Its flags come from `claude --help`.** `--output-format stream-json` with `--include-partial-messages` streams text as it's written (print mode refuses stream-json without `--verbose`), `--json-schema` asks for structured output, `--system-prompt` replaces Claude Code's own instructions with the app's, `--tools ""` turns off the built-in tools, and `--no-session-persistence` keeps these runs out of the user's session list. The prompt goes in on standard input, so a long posting can't hit a command-line length limit.
- **The plan login, never an API key.** `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` are removed from the child's environment, because either one makes `claude` bill an API account. The child runs in an empty temporary folder so no project settings or files leak into a step.
- **Structured output with a fallback.** The final `result` line carries `structured_output` when the schema was met. If it's missing, the result text is checked against the same schema instead, and the prompt ends with "Reply with JSON only", so either path gives validated data.
- **Finding `claude`.** A Mac app opened from Finder doesn't get the shell's `PATH`, so besides `PATH` the provider checks `~/.local/bin`, `~/.claude/local`, `/opt/homebrew/bin` and `/usr/local/bin`. Settings shows whether it's installed and signed in, from `claude --version` and `claude auth status --json`.
- **Tests use a fake `claude`.** A small script records the arguments, environment, folder and input it gets, and prints the same stream-json lines. These tests are skipped on Windows, where a `.cmd` stand-in can't receive an argument with newlines in it.
- **ChatGPT (Codex) provider.** It runs each step through `codex exec`, so the work uses the user's ChatGPT plan instead of API credits. It's for personal use, like the Claude Code provider. The flags were read from `codex exec --help` (codex-cli 0.169.0), not guessed: `--output-schema` takes the step's schema as a file, `-o` writes the final answer to a file, `--json` prints events, `-s read-only` keeps the agent from changing anything, `-C` with `--skip-git-repo-check` runs it in an empty temporary folder, `--ephemeral` keeps the runs out of the session history, and `--ignore-user-config` skips the user's own config (and any tools it sets up) while still using their sign-in.
- **Codex's answer comes from the `-o` file, not the event stream.** The `--json` events for a failed turn were checked against the real CLI (`thread.started`, `turn.started`, `error` while it retries, `turn.failed`), but a successful reply needs a real sign-in, which CI doesn't have. The file is written by Codex itself, so reading it doesn't depend on the event format. The events are used for streaming text, token counts and failures, and an `error` event alone isn't a failure, since Codex prints them while it reconnects.
- **Codex has no system prompt flag,** so the instructions, the resume and the step's message go in one prompt on standard input.
- **Signed in means signed in with ChatGPT.** `codex login status` prints "Logged in using ChatGPT" for a ChatGPT sign-in and "API key configured" for a key. Only the first counts, since the point of this provider is the plan. `OPENAI_API_KEY` and `CODEX_API_KEY` are removed from the child's environment for the same reason.
- **The default model is Codex's own.** The setting is stored as "default" and no `-m` is passed, so the plan's current model is used. A model typed in Settings is passed through as given.
- **Codex's tests run on every system.** Its arguments have no line breaks (the schema is a file and the prompt is on standard input), so a `.cmd` stand-in works on Windows, unlike the fake `claude`.
- **A refusal or a cut-off reply is an error,** reported as `BadOutput` with the reason, because half a JSON reply can't be checked against the schema.
- **The Demo provider is offline and deterministic.** It builds replies from the request itself, so the whole flow runs with no key or network, and end-to-end tests get the same output every time. Its score is a simple count of specific and vague bullets, and the interface says so.

## The tailoring steps

- **Three steps: Score, Rewrite, Done.** Each is a separate call with its own schema, so each streams into its own part of the interface and can be rerun alone. The flow went through two earlier shapes. Red flags, Rewrite, Review rewrote before scoring, so the rewrite never saw the ATS feedback. Diagnose, Rewrite, Re-score fixed that but put a lot on screen: two scores, skipped sections, keyword lists and a per-change breakdown. The current one keeps what drives the rewrite and drops the rest.
- **Score is small so it's fast.** One ATS score and three red flags, a short prompt, no facts bank and a 1,500-token cap. A Claude provider runs it on Sonnet even when Opus is chosen, because this step is where speed shows most.
- **The rewrite waits for the user.** Score stops with a note box and a Rewrite button, so detail the resume lacks can go in before anything is rewritten.
- **The note becomes facts.** It's split in code into one fact per line or sentence and saved to the facts bank, which the rewrite and the checker already use. Splitting in code keeps it instant and predictable. The run records which facts its note added, so Undo can remove exactly those, and it checks again any rewrite that cited one. A fact that was already in the bank isn't counted as the note's, so Undo never removes it.
- **Missing keywords come from the coverage count,** the posting's required and preferred skills the person can back up but doesn't show. No model is asked, so the list costs nothing and can't include a skill without evidence.
- **Only change what a red flag or keyword calls for.** The prompt says so, and the model returns every other bullet unchanged.
- **Never less specific, checked in code.** `dropped_specifics` runs the grounding check backwards: every number, name and skill in the original bullet must be in the rewrite. A rewrite that drops one gets a warning naming what it lost. Prompting alone wasn't enough, since a "simpler" rewrite tends to lose the tools.
- **Bold is kept in code.** Models drop formatting, so `keep_bold` restores the template's bold on phrases that survive a rewrite and allows one new bold phrase for the key result, only from words already in the bullet. A change that only moves bold counts as no change.
- **Your words are never blocked.** A request in "Anything to add?" is applied by the app with the note as its source, and a hand edit is the person's own text, so neither goes through the fabrication check. The check is for what the model writes on its own.
- **The model's unsupported claims need your OK, they aren't refused.** A rewrite the model made with a number, name or skill the sources don't back up is marked "Needs your OK" with the reasons, and Accept works on it. The person knows things the facts bank doesn't; a disabled button only sent them to edit the LaTeX by hand.
- **Only truth problems need an OK.** A rewrite is flagged only when a number, name or skill in it isn't backed up by its sources. Style findings and dropped details show as a warning with Accept still enabled: they are judgement calls, and the person reading the bullet is better placed to make them than a rule. Rewrites with warnings still go back to the model once, and the retry is kept only if it has fewer warnings.
- **Accept or Keep original, nothing else.** Hand edits, copy and the "How many…?" questions are gone from the screen. The note box covers what the questions did, before the rewrite instead of after it. The backend still checks a hand edit if one is sent.
- **Done is one call, not two.** Scoring base and tailored in separate calls let run-to-run noise turn a gain into a loss (58 to 54 in one run). Done puts both resumes in one message and scores them with the same rubric as Score.
- **Older runs still open.** Runs saved by the earlier steps are read into the new shape: their red flags and ATS scores carry over and the rest is dropped.
- **The run keeps the posting's link** when it started from Jobs, so every step can show "Company · Role · View posting".
- **The base resume is the cached context.** Every step sends the same system instructions and the same plain-text resume (with bullet ids) first, then the step's own message, so providers that cache a repeated prefix only pay full price for it once per run.
- **One automatic repair.** Blocked rewrites go back to the model once, with the checker's reasons. In the same call, when the first answer changed nothing or added none of the missing keywords, the unchanged lines go back with the advice listed as items to address. A line returned with its own text is no edit. A second failure stays blocked and the user sees why. A retry that fails outright keeps the first attempt's results, since those are already checked. The "unsupported claims caught" count comes from the first attempt, before the retry, so it measures what the model tried to add.
- **Every line gets a result.** A line the model skipped comes back unchanged. A change to a line the model may not edit (a date, an employer) is checked and blocked, so it shows as a blocked card instead of vanishing. An id that isn't a line of the resume is counted in the run's summary.
- **The whole resume is addressable, with protected facts.** Bullets in every section, coursework, skills lines, tech stacks and honors are prose the model may rewrite. Dates, GPA, school, degree, employer, job titles, locations and an honor's name and numbers are facts it must keep word for word. The check is literal: each protected piece must still be in the new text. That is stricter than the grounding check, which would let a date be swapped for another date found elsewhere on the page.
- **A note's instruction is applied in code, not by the model.** "change graduation date to 2027" is resolved to one line and applied as written, with the note as its source, so it can't be refused or reworded. It starts accepted and shows the note it came from, with Undo. The model isn't sent that line. A note that could mean more than one line changes nothing and asks which, since guessing at someone's dates is worse than asking.
- **Every advice item and note gets a result.** The model reports on each item, and code checks the report against what happened to the lines. A keyword or a note's fact counts as applied only when the page shows it, whatever the model says.
- **Skills lines are rewritable.** Technical Skills lines go to the rewrite with their own ids (`s1`, `s2`), so a skill the person has but doesn't show can be added where it fits. Every skill on the line has to be backed up like any other claim, and dropping one is a warning. A change of order alone is no edit, since export orders the line anyway.
- **The note's facts always count.** Facts added under "Anything to add?" are listed in the rewrite prompt and count as sources in the check whether or not the model cites them. The person typed them for this posting, so a rewrite shouldn't be blocked because the model forgot an id.
- **"No changes needed" means it.** The message only appears when the score gave no advice and the person added no notes. Otherwise the summary says what happened: lines returned unchanged, rewrites blocked and why, bold-only changes, or a failed second try. A failed call is an error, never an empty result.
- **Command-line providers have a watchdog.** Claude Code and Codex are stopped after 600 seconds in all, or 240 seconds with no output, and the step fails with that reason. Claude Code's answer is used as soon as its result line arrives, without waiting for the command's output to close.
- **A rewrite always cites its own bullet.** If the model leaves its own id out of `sources`, it's added before the check.
- **Summary advice is dropped in code.** A red flag that says to add a summary, objective or profile is removed. This sits on top of the locked section order in the template engine.
- **Skills reordering is done in code at export:** within each skills line, required matches first, then preferred, then other mentions, then everything else in its original order. Nothing is added or dropped by the reordering, and an honors or awards line is left alone. An accepted rewrite of a skills line is written with the same order.
- **One-page trimming hints.** When the PDF runs over a page, the app lists bullets whose last line is shortest, using about 113 characters per bullet line (measured on the compiled sample), so a small cut saves a whole line. It's an estimate; the next compile is the real check.
- **Model text is tidied** before checking: a leading bullet mark, wrapping quotes and a final period are removed, because the template's bullets have none.
- **Cost per run.** `pricing.py` has per-token prices for the Claude API models. Claude Code and Codex bill the user's plan, Gemini's free tier, Ollama and the Demo provider cost nothing, and an unknown model shows a dash rather than a guess. Cache writes cost 1.25 times the input price, and cache reads are priced per model.

## Desktop window and bridge

- **pywebview with one entry point.** The page reaches Python through a single method, `Bridge.call(command, args)`, which runs a command from the `COMMANDS` list and answers `{ok}` or `{error: {kind, message}}`. With one entry point, argument names, error handling and the allowed commands all live in one place, and no other method on the object can be reached from the page. A test checks that `call` is the only public attribute.
- **No web server, no open port.** Vite builds the interface into one self-contained `index.html`, with scripts, styles, fonts and pdf.js inline (`vite-plugin-singlefile`). The window loads it from a `file://` URL, and pywebview's own HTTP server stays off. The webviews block module scripts fetched from `file://`, but scripts written inline in the page run fine.
- **pdf.js on the main thread.** Loading pdf.js's worker module into the page lets it run without a separate worker file, which a single-file build can't ship. It only ever draws one page.
- **Streaming through channels.** A streaming command gets a channel id from the page. Python sends each event with `window.run_js("window.__tailorEmit(id, event)")`. `run_js` doesn't wait for the page, so streaming never slows a step, and `json.dumps` escapes the text so a posting can't break out of the script.
- **Calls run on their own threads.** pywebview runs each call on a new thread, so a long model step doesn't freeze the window. Changes to a run go through one lock and always apply to the latest saved state, so a decision made while a step runs isn't overwritten when the step finishes.
- **The page waits for the bridge.** pywebview adds `window.pywebview.api` just after the page loads and then fires `pywebviewready`. The app always opens the page from a `file://` address, so a page loaded from `file://` (or one that already has `window.pywebview`) waits for that event. Served over http, as in screenshots and the browser tests, it uses an in-memory mock backend with the fake sample data instead. An earlier version marked the app with `?desktop=1` on the URL. That broke on Windows: pywebview passes the URL to .NET's `Uri`, which treats a `?` in a file URL as part of the file name, so WebView2 showed "File not found". The window URL now has no query string, and a test checks that.
- **The process ends itself when the window closes.** pywebview runs each bridge call on a thread that Python waits for at exit, and the call hands its result back to the page with `evaluate_js`, which on macOS waits forever once the window is gone. A call still running at close, such as a model step, would leave the app alive with no window. One CI run showed it: the self-test passed and wrote its report, then never exited. After the window closes, `leave` closes the database and calls `os._exit`. Every change is already saved by then, and SQLite rolls back any write that was cut short.
- **CI opens the packaged window.** The self-test on each installer build opens the real window with a throwaway data folder and an in-memory key store. It waits for the page to report the Python backend, makes one bridge call, then closes. Checking that the webview module imports wasn't enough to catch the Windows bug above.
- **The preview fits its box.** The PDF page is scaled by the smaller of the pane's width and height ratios (`fitScale`), so the whole page shows with no scrolling or panning, and a resize observer redraws it when the pane changes size. Fitting by width alone made a short, wide pane cut off the bottom of the page.
- **The PDF is named after the person on the resume.** The name comes from the resume's `\Huge` header line, so nothing personal is built into the app: the sample exports as `Jordan_Sample_Resume_<Company>.pdf`.
- **Two kinds of interface tests.** Playwright drives the page against the mock backend for the interactions. A second test opens the built `index.html` from `file://` against the real Python bridge (Demo provider and Tectonic) and runs the flow to an exported PDF, checking on the way that the preview fits the pane at three window shapes. A test-only HTTP front (`tests/bridge_server.py`) stands in for pywebview there. The app itself has no server.

## Storage

- **SQLite through `sqlite3`, with plain SQL.** Runs, applications, step logs, grounding blocks, the manual baseline and settings each have a table. A run's full state is stored as JSON next to the summary columns that the history list and the numbers need, so reopening a run restores it exactly. `PRAGMA user_version` records which migrations a file has had.
- **One connection behind a lock.** Calls arrive on several threads. One connection opened with `check_same_thread=False`, and every statement run under a lock, is simpler than a connection per thread, and the app's writes are small.
- **API keys in the system keychain** through `keyring`: the macOS Keychain and the Windows Credential Manager. The interface only gets a masked form, the first 6 and last 4 characters.
- **The data folder** is the OS app-data folder (`~/Library/Application Support/Tailor/private` on a Mac, `%APPDATA%\Tailor\private` on Windows). `TAILOR_DATA_DIR` overrides it, for development against the gitignored `data/private/`.

## Settings and data

- **Each run keeps the resume it started from.** The base resume's text is stored with the run (migration 2 adds the column). A run's bullet ids point into that text, so replacing the base resume in Settings can't break or change an earlier run. Runs saved before the column existed fall back to the current base resume.
- **Moving the data folder copies, then switches.** The chosen folder is recorded in `location.json` beside the default data folder, where the app looks before opening anything. An empty folder receives the data as it is, a folder with other files in it gets a `Tailor` folder inside, and a folder that already holds Tailor data is used without copying. The old copy is left in place, so a failed or mistaken move loses nothing. `TAILOR_DATA_DIR` still wins, and the app refuses to move data while it's set.
- **Line endings are kept.** `.tex` files are read with `newline=""`. `Path.read_text` turns Windows CRLF into LF, which changed a resume saved on Windows on its way in.
- **Reduce Motion follows the system setting** through `prefers-reduced-motion`, so there's no separate switch in the app to fall out of step with it.

## Facts import

- **Files and pages in, suggestions out, nothing saved without approval.** A dropped PDF, Word, text or Markdown file, or a web page, is turned into text, and the selected provider suggests short, specific facts from it. The interface saves only the ones the user accepts, as they are or edited.
- **Suggestions are checked like rewrites.** Every number, name and skill in a suggested fact must appear in the document, using the same grounding check as rewrites. A suggestion that fails shows why and can't be accepted as it is. Editing it makes it the user's own statement, which the facts bank exists to hold. Suggestions already in the bank are marked, and repeats are dropped.
- **Only facts that add something are offered.** The model sees the resume and the saved facts and is told to skip what they already say. Code checks anyway, because the model doesn't always listen: a suggestion is covered when one bullet (with its role or project heading), skills line or saved fact supports every number, name and skill in it, and shares at least half of its words (four fifths when it has no names or numbers to check). Covered suggestions sit in a closed "Already on your resume (N)" group with what covers them, so nothing is hidden for good but nothing old gets in the way. The check uses one source at a time on purpose: a fact that joins two bullets into a new claim counts as new.
- **Libraries.** `pypdf` reads PDFs (it's already used for page counts), `python-docx` reads Word files, including table cells, where resumes often keep their content, and `beautifulsoup4` with Python's built-in HTML parser pulls the readable text out of a page and drops scripts, styles, navigation and footers.
- **Resume links on a page.** Links whose address ends in `.pdf` or whose text says resume or CV are listed, so a portfolio page can lead on to the resume itself. Reading one is the user's choice.
- **Limits.** Files over 10 MB are refused before they're sent. Text over 60,000 characters is cut, and the interface says so instead of quietly dropping the rest. A scanned PDF with no text says that there's nothing to read.
- **Dropped files cross as base64.** The page reads a dropped file with `FileReader` and sends its bytes to Python. Webviews don't give the page a dropped file's path, and sending the bytes works the same in every webview.
- **Web requests name the app, not the user.** The user agent is a plain `Tailor/0.1` string. Only `http` and `https` addresses are fetched.

## Jobs

- **Three fixed sources.** The listings come from SimplifyJobs/Summer2027-Internships, vanshb03/Summer2027-Internships and speedyapply/2027-SWE-College-Jobs and nowhere else. There's no way to add a repo, because each one needs its own parser.
- **Raw files from GitHub.** The files are downloaded from `raw.githubusercontent.com`, which needs no token and has no API rate limit.
- **Structured data first.** Simplify's `listings.json` holds every listing with an `active` flag and a posting time, so it's read first. vanshb03 publishes one in the same format. SpeedyApply has no data file at any of the usual paths, so its README tables are parsed. Simplify's README is the fallback if its JSON fails. The tables sit between generated `TABLE_*_START` and `TABLE_*_END` markers, so their layout is stable, and columns are found by header name in case one gains or loses a column.
- **Internships only.** SpeedyApply's `README.md` and `INTERN_INTL.md` are read. Its new grad files aren't.
- **One entry per posting.** The same posting in two repos is merged by its address without tracking parameters, and lists both sources. Its earlier date wins. vanshb03 links through its own short links, so across different lists the same company and title in an overlapping place counts as the same posting too. Within one list it doesn't: the same title in two cities is two postings there.
- **Master's and PhD roles are hidden by default.** Each list's own marker is used first (Simplify's degrees field and its 🎓), then the title. A role that also takes a Bachelor's isn't hidden, whatever its title says. A toggle shows them.
- **US by rules, not a city list.** State names and codes, DC, Puerto Rico, the country's names, remote in the US, and a short alias list for cities written without a state. A city list would need every town an internship is in. Canada is checked first because "CA" is also California. The rules were checked against all 1,211 distinct location strings in the three lists; the ones they can't place ("Remote", "Multiple Locations Available") aren't counted as US.
- **The cache is a JSON file in the data folder,** next to the facts bank. It can be rebuilt from the repos at any time, so it doesn't need a table. A repo that fails keeps its last listings, and if both fail nothing changes.
- **New means first seen since the previous visit.** Each listing keeps when the app first saw it. A listing first seen after the previous visit opened gets the badge, including ones that arrive in this visit's own refresh.
- **Reading a posting is a guess.** The page reader from the facts import fetches the link. Workday and similar sites build the posting with JavaScript or block plain requests, so a page under 600 characters of text counts as unreadable. The Tailor screen then opens with the company and role filled in and asks for a paste, with a button that opens the posting in the browser.
- **Applications keep their link.** A new `url` column on the applications table (migration 3) holds it. Marking the same listing applied twice updates one entry.
- **Links open in the default browser,** through an `open_url` command that only accepts `http` and `https`, so a link never opens inside the app window.

## Autofill extension

- **Its own folder, its own build.** The extension is in `extension/` with its own `package.json`, so the desktop app and the extension don't share build tools. It's Manifest V3, plain TypeScript and plain DOM: no framework for a profile page and a few buttons.
- **esbuild bundles it.** Chrome loads a content script as a plain script, not a module, so each entry (content, popup, profile page) is bundled into one file. esbuild does that with no configuration beyond `build.mjs`. It's the only build dependency; `@types/chrome` and `@types/node` are for type checking only.
- **Everything stays in `chrome.storage.local`.** The profile and the resume (as a data URL, capped at 5 MB) never leave the browser. The extension has no network calls, no analytics and no remote code.
- **Few permissions.** `storage`, `activeTab` and `scripting`, plus a content script on the four job sites only. On any other site the popup adds the script to that one tab when the person clicks Autofill, which `activeTab` allows, so the extension never asks to read every site.
- **The site's own field names first, labels second.** Greenhouse ids, Lever names, Ashby's `_systemfield_*` and Workday's `data-automation-id` are steadier than wording. Everything else, and every field on other sites, is matched by its label with ordered rules (`keys.ts`): "First name" is tried before "Name".
- **Values are set the way typing sets them.** React forms ignore a value written straight onto an input, so the browser's own value setter is used and `input` and `change` events are fired. A resume goes in through a `DataTransfer` file list, the only way a page can set a file input.
- **Choices are matched by meaning.** A select, a radio group, a pair of Yes/No buttons or a searchable dropdown gets the closest choice: exact text first, then any of the usual decline wordings for "Decline to answer", then a leading Yes or No, then shared words. A "no" answer ("I am not a protected veteran") can't match a "yes" choice.
- **What it won't do.** It never submits or presses Next, never ticks a single checkbox (those are consents and agreements), never overwrites an answer already there, and leaves open questions blank. Everything it leaves is counted and outlined, so nothing is silently skipped.
- **Workday one page at a time.** Each press fills the page that's showing. Moving on is Workday's own Save and Continue, so the person reviews each page before it's saved.
- **Real input on Workday, through the debugger.** Workday's widgets didn't take dispatched events, twice. A content script can't send trusted input, so the extension's service worker attaches Chrome's debugger to the one tab for one fill and sends Input.insertText, Input.dispatchKeyEvent and Input.dispatchMouseEvent. The cost is a permission and a bar while it runs; the alternative was guessing which fake events Workday wants. Every real click first checks that its point hits the element, because a page that's redrawing can move things between measuring and clicking.
- **Find every element again before using it.** Workday replaces a section's elements when it redraws it (a ticked box, a chosen dropdown, Add). An element found earlier then takes typing that goes nowhere and reads back as filled. Fields are found again by id, or by their path from the nearest ancestor with one, before every step and every check; sections are found again after every Add.
- **A test that can fail.** Saved pages can't show whether Workday's form took a value, so the extension is also run in Chromium on a stand-in form that keeps its own state and only takes real input where Workday appeared to. The stand-in is a model of Workday, not Workday; the debug report from a real application is what confirms a fix.
- **Debug reports carry no values by default.** Labels and the page's own error messages are recorded as they are; what was typed is recorded as a length and whether it matches, unless the person asks for values.
- **Test samples are rebuilt, not captured.** The job sites are blocked from the development environment, and Workday only shows application pages after signing in. The samples in `extension/test/fixtures` are rebuilt from each site's known form structure, and each file says so. The built extension was also run in Chromium on those samples, with the content script loaded at each site's address. Saving a real application page from Chrome into the fixtures folder is the way to add a site's actual markup. Workday now has three such pages (`extension/test-fixtures/workday_*.html`): only the application form is kept, without scripts, styles, the page header or the session token, and personal values are replaced. The originals stay in `test-fixtures-private/`, which git ignores.
- **On Workday, a value on screen isn't an answer.** Workday shows typed digits in a date and typed text in a search list without taking either. So every Workday field is checked after it's filled (the display, `aria-valuenow`, a chosen chip, the button's text, errors), retried once, and reported as "Filled but not accepted" when it still isn't taken, instead of being counted as filled.

## Interface blocks

- **Bencho's code and comments are kept as written.** `ui/src/blocks/SOURCE.md` lists each block, where it came from and its license, and whether the file is Bencho's original or a version written for this app from the public listing.
- **Tokens are mapped on each block's own root.** A Bencho block reads tokens such as `--fill-on`, `--fill-slab` and `--font-ui`. Each one is set on the block's root element to the app's own token (`--fill-on: var(--wake-ink)`, `--signal: var(--accent)` and so on), so Bencho's CSS stays as written and nothing new becomes global.
- **The upload dropzone gets a real-file mode.** Bencho's block is a demo that uploads pretend files from a tray. With an `onFile` prop it takes real drops and clicks instead, hides the tray, and holds its bar at 90% until the file has been read. The additions are marked `app:` in the file. Without the prop it's Bencho's block unchanged.
- **Two ASCII wakes.** Bencho's ASCII wake follows the pointer, which suits the empty state. A loader that drives the same effect by itself while a step runs is a separate, rebuilt file.

## Compiling to PDF

- **Tectonic 0.15.0, pinned.** It is the newest release with ready-made builds for Apple Silicon Macs, Windows and Linux. A pinned version means every build ships the same Tectonic, and the download script needs no GitHub API call to pick one.
- **The download script unpacks archives in Python.** `scripts/fetch_tectonic.py` uses `tarfile` and `zipfile`, so the same code runs on every OS. Shelling out to `tar` would depend on which `tar` comes first in `PATH`, and on Windows Git Bash's `tar` reads `C:` as a remote host name.
- **Where the app looks for Tectonic**, in order: the path set in Settings, `TAILOR_TECTONIC`, the bundled copy (`packaging/bin/` in development, the PyInstaller folder in a build), `PATH`, then the Homebrew and Cargo folders, which a Mac app launched from Finder doesn't have in its `PATH`.
- **XeTeX wrapper.** Tectonic runs XeTeX, and the template's `\input{glyphtounicode}` and `\pdfgentounicode=1` only exist in pdfTeX, so compiling the file directly fails with "Undefined control sequence". Each compile writes `tailor_main.tex`, which defines do-nothing versions of both commands when they are missing and then `\input`s the resume. The user's file is never edited. XeTeX writes Unicode text into the PDF by itself, so ATS parsers can still read it. A test compiles the sample without the wrapper and checks that it fails.
- **One Tectonic run at a time.** On Windows, two runs that build Tectonic's format file at the same moment fail with "Access is denied". `compile_tex` holds a `threading.Lock` while Tectonic runs. A test starts four compiles at once against a fake Tectonic that records overlaps, and it fails if the lock is removed.
- **Five-minute compile timeout.** The first compile downloads TeX packages, which took about 30 seconds on a fast connection. The limit leaves room for a slow one.

## Packaging

- **PyInstaller, one folder.** `packaging/tailor.spec` builds a folder app rather than a single self-extracting file, so the app starts without unpacking itself to a temporary folder on every launch. On macOS the folder is wrapped as `Tailor.app` for Apple Silicon (`arm64`).
- **What's bundled.** Tectonic sits at the top of the bundle, where `find_tectonic` looks first in a packaged app. The built `index.html` goes in `ui/`, and the skills lexicon and python-docx's data files come along. keyring finds its backends at runtime, so the macOS and Windows ones are named as hidden imports.
- **Ad-hoc signing on the Mac.** CI signs the `.app` with `codesign --force --deep --sign -`. An unsigned app downloaded from the internet can show as "damaged" on Apple Silicon. An ad-hoc signature avoids that without a paid developer certificate; macOS still asks before the first open. The README has the `xattr -cr` fallback for a copy that still won't open.
- **A `.dmg` for the Mac, an Inno Setup installer for Windows.** `hdiutil` makes the disk image. Inno Setup installs for the current user, so no administrator prompt appears, and it adds a Start menu entry and an uninstaller. Windows 10 and 11 already include the WebView2 runtime that pywebview uses.
- **Every build tests itself.** `Tailor --self-test report.json` runs inside the packaged app without opening a window. It checks the bundled interface, the lexicon, the keychain backend and the webview backend, and compiles a small document through the XeTeX wrapper with the bundled Tectonic. CI runs it on each build before uploading the installer, so a bundle missing a file fails the build instead of failing on a user's computer. It writes to a file because a windowed app on Windows has no console.

## Tests and CI

- **Tests that need Tectonic** are skipped when it isn't installed, so a fresh checkout can run everything else. CI sets `TAILOR_REQUIRE_TECTONIC=1`, which turns a missing Tectonic into a failure.
- **CI runs the tests on Linux, macOS and Windows**, because the compile lock and the Tectonic download both behave differently on Windows.
